# 伴奏/人声分离 → 干声转音符 → 写进 SV2

## 为什么不能全在 SV2 里做

SV2 **自带**「音频转音符」,但**只在界面里** —— 官方脚本 API 的 26 个类里:

| 查过的东西 | 结论 |
|---|---|
| 音频读写 / 渲染 / 导出 | **没有**任何类 |
| `NoteGroupReference#isInstrumental` | **只有 getter**,没有 setter、没有设文件路径的方法 ⇒ 脚本连音频文件都导不进去 |
| `Track#isBounced/setBounced` | 只是"渲染面板里是否导出"的**开关**,真渲染是界面操作 |

既有实现的结论完全一样,它的手册里写着:

> ⚠️ **提醒用户用 SV 自带的转录功能** —— 音频转音符这件事**我们的脚本 API 做不到**

所以链路必然是:**音频处理在 SV2 之外 → 结果用桥的 `write_notes` / `write_pit` 写进去**。

## 链路

```
① 分离伴奏/人声         ② 音频分析              ③ 写进 SV2
   MSST-GUI 等本地工具  →  analyze-audio.py   →  align_audio(对齐+速度标)
   (SV2 做不到)            analyze-chords.py     write_notes(音符/和弦)
                           import-musicxml.py    write_pit / set_note_attrs

④ 干声 → 音符           ← **用 SV2 自带的「音频转音符」**
   (落在最上面那条轨,是个可自由移动的音符组)
```

第 ③ 步是桥的能力,已经真机验过;①②④在 SV2 之外或在 SV2 界面里。

## 关于「干声转音符」:CREPE 那套**已删**

一开始我移植了参考项目的 CREPE onnx 方案(extract-notes.py),自检还逼出了它三个缺陷:

| # | 参考项目的问题 | 处理 |
|---|---|---|
| ① | **单个低置信帧就切断音符** —— MAX_GAP_SEC 那个 60ms 容差在帧被判无声这条路上**从来没生效过**,换气/辅音/颤音低谷会把一个音切成好几段 | 低置信帧只当作洞,洞宽超过容差才收尾 |
| ② | **滤短块与合并的顺序错了** —— 两个同音块之间夹着一个 1~2 帧的异音块,它先被滤掉,于是两个同音块永远合不上 | 改成 **先滤短块 → 再合并同音相邻块 → 最后去八度假音** |
| ③ | **起音八度假音** —— 起音瞬态是宽带的,CREPE 偶尔锁到高八度 | 保守判据去掉(短 + 与邻居正好八度 + 明显比邻居短) |

效果确实比参考项目好(合成 8 音旋律:它 13 个夹假音,本实现 **8 个精确匹配**)。

**但最后还是删了** —— 因为 **SV2 自带的「音频转音符」质量更好**,而这一环本来就不必自己造。
删掉的是:extract-notes.py / fetch-crepe.py / check-audio-deps.py、CREPE 模型(6.2MB)
与 onnxruntime 及其专属依赖 —— **共约 48MB**。

> 留档的意义:那三条缺陷是**自检逼出来的**,不是看代码能发现的。哪天要再碰音高检测,
> 这三条仍然适用。


## 完整链路(现在能跑通的)

```
① 分离伴奏/人声         ② 测 BPM / 第一拍          ③ 对齐
   MSST-GUI 等本地工具  →  analyze-audio.py      →  align_audio(桥)
   (SV2 做不到)            (纯 numpy)               把音频挪到锚点 + 写速度标

④ 转录                  ⑤ 清理                    ⑥ 精修
   SV2 自带的音频转音符  →  get_layout 体检重叠   →  apply_lyrics 填歌词
   (落在最上面那条轨)      quantize 吸附网格         align_lyrics 按 LRC 对位
                                                    write_pit 画音高线
                                                    set_note_attrs 改音素/属性
```

**②③ 是新增的**。`analyze-audio.py` 用纯 numpy 实现(不需要 librosa),自检踩了两个真坑:

| 坑 | 现象 | 修法 |
|---|---|---|
| **半速/倍速歧义** | 120 BPM 被测成 60.03 | 自相关乘一个以 120BPM 为中心的对数正态**速度先验** |
| **分析窗延迟** | 第一拍 0.35s 被测成 0.279s | 帧覆盖 `[i·HOP, i·HOP+FRAME)`,通量在"起音刚进窗"就起峰 ⇒ 补 `(FRAME−HOP)/sr` |

修完自检 **119.79 / 0.3483s,PASS**。

**关于"转录落在最上面那条轨"**:脚本 API **没有**调整轨序的能力
(`Track` 只有 `getDisplayOrder()` 没有 setter,`Project` 没有 `moveTrack`),
所以"新建一条空轨放最上面"做不到。能做的是**把最上面那条轨腾空** ——
`track_ops list` 报 `displayOrder` + `noteCount`(⚠️ 找视觉最上面要用 `min(displayOrder)`,
显示顺序可以和存储下标不同),再用 `group_ops {action:"move"}` 把它的组挪走。

## 关于"声库风格移植":换了一条更安全的路

参考项目那套是对**声库文件**做手术(nofs 里的 32 个 float32 向量),只对 **flat(非加密)** 版
声库有效,而且是在改用户装好的声库 —— 风险与许可都不明朗。

但脚本 API **本来就有** `NoteGroupReference:getVoice()/setVoice()`,它管的是**这一组**的默认声音属性:

```
paramLoudness / paramTension / paramBreathiness / paramGender / paramToneShift
vocalModeParams: { <模式名>: { pitch, timbre, pronunciation } }
```

也就是"把某个风格套到这一组上" —— **目的完全一样,但一个字都不碰声库文件**。所以桥里加了:

| op | 作用 |
|---|---|
| `get_voice` | 读当前组的默认声音属性 |
| `set_voice` | 改它(逐项范围校验);或 `preset:"<声库名>/<预设名>"` 直接套用 |
| `list_voice_presets` | 读 SV2 自己的 `voice-presets.json`,列出"哪个声库有哪些预设" |

> `voice-presets.json` 在 `%APPDATA%\Dreamtonics\Synthesizer V Studio 2\settings\`,
> 里面存着用户存好的预设(含 `Airy` / `Soft` / `Bright` 等 vocal mode 的 pitch/timbre/pronunciation)。
> 桥用 Lua 的 `io` 直接读它 —— 那是**只读**的,不动任何声库。

> ⚠️ `set_voice` 实现成**读—改—写整个对象**:官方没说 `setVoice` 收不收"局部"对象,
> 而写回一个残缺对象有可能把没提到的属性清掉。
